## 1. Conventions

### 1.1 Basics

| Topic | Convention |
|---|---|
| Base path | `/api/v1` (same origin as the SPA) |
| Format | JSON, UTF-8. `Content-Type: application/json`; uploads use `multipart/form-data` |
| Naming | JSON fields `camelCase`; URL paths `kebab-case`; enum values `UPPER_SNAKE_CASE` |
| IDs | UUID strings. Public URLs use product `slug` and `orderNumber` |
| Timestamps | ISO 8601 UTC, e.g. `"2026-11-20T10:30:00Z"`; dates as `"2026-11-24"` |
| Money | `{ "amount": 1299, "currency": "EUR" }` — `amount` is an integer in **minor units** (cents), gross incl. VAT |
| Versioning | URL version (`/v1`). Breaking changes → `/v2`; additive changes are not breaking |
| Language | `Accept-Language: de` / `en` (the SPA sends the language of the page) for localised messages and content (§1.7) |

### 1.2 Authentication and CSRF

- Session cookie (`SESSION`, `HttpOnly`, `Secure`, `SameSite=Lax`) created by
  `POST /auth/login`. No tokens in `localStorage`.
- CSRF: the server sets a readable `XSRF-TOKEN` cookie; every `POST`, `PUT`,
  `PATCH` and `DELETE` must send it back as the `X-XSRF-TOKEN` header.
  Exception: payment-provider webhooks (verified by signature instead).
- Guest carts: `CART_TOKEN` cookie (`HttpOnly`), handled transparently by the server.

**Access levels used below:** `public` · `customer` (logged in, any role) ·
`admin` (role `ADMIN`). Customer resources are always scoped to the current
user — another user's resource returns `404`, not `403`, to avoid leaking existence.

### 1.3 Pagination, sorting, filtering

```
GET /api/v1/products?page=0&size=24&sort=price,asc
```

```json
{
  "items": [ ... ],
  "page": 0,
  "size": 24,
  "totalItems": 137,
  "totalPages": 6
}
```

`size` max 100. Multi-value filters are repeated or comma-separated:
`?colour=blue&colour=red` ≡ `?colour=blue,red`.

### 1.4 Error format

All errors use **RFC 9457 Problem Details** (`application/problem+json`) with a
stable `code` the frontend can switch on:

```json
{
  "type": "about:blank",
  "title": "Insufficient stock",
  "status": 409,
  "detail": "Only 4 animals of 'Blue Dream' are available.",
  "code": "INSUFFICIENT_STOCK",
  "instance": "/api/v1/checkout/orders",
  "traceId": "4f1c2a…",
  "errors": [
    { "field": "items[0].quantity", "code": "INSUFFICIENT_STOCK", "message": "Max. 4 available" }
  ]
}
```

| HTTP | Typical `code` values |
|---|---|
| 400 | `VALIDATION_FAILED`, `MALFORMED_REQUEST`, `WEBHOOK_SIGNATURE_INVALID`, `WEBHOOK_INVALID` |
| 401 | `UNAUTHENTICATED`, `INVALID_CREDENTIALS` |
| 403 | `FORBIDDEN`, `CSRF_INVALID`, `EMAIL_NOT_VERIFIED` |
| 404 | `NOT_FOUND` |
| 409 | `SLUG_TAKEN`, `SKU_TAKEN`, `SCIENTIFIC_NAME_TAKEN`, `IN_USE`, `INSUFFICIENT_STOCK`, `PRODUCT_UNAVAILABLE`, `CART_EMPTY`, `CART_CHANGED`, `PRICE_CHANGED`, `SHIPPING_PAUSED`, `SHIPPING_METHOD_UNAVAILABLE`, `PAYMENT_METHOD_UNAVAILABLE`, `ORDER_NOT_CANCELLABLE`, `ORDER_ALREADY_PAID`, `ORDER_NOT_PAYABLE`, `INVALID_STATUS_TRANSITION`, `PAID_BY_PROVIDER`, `ACCOUNT_NOT_LOCKABLE`, `CODE_TAKEN`, `COUPON_IN_USE`, `NOT_REFUNDABLE`, `REFUNDS_CHANGED`, `IDEMPOTENCY_KEY_REUSED`, `CONFLICT` (optimistic lock), `DUPLICATE` |
| 422 | `CART_FULL`, `VERSION_REQUIRED`, `SLUG_INVALID`, `NO_ACTIVE_VARIANT`, `NO_IMAGE`, `SPECIES_RESTRICTED`, `LAST_IMAGE`, `IMAGE_TYPE_UNSUPPORTED`, `IMAGE_INVALID`, `IMAGE_TOO_LARGE`, `IMAGE_TOO_SMALL`, `IMAGE_LIMIT_REACHED`, `IMAGE_ORDER_INVALID`, `COMPARE_AT_PRICE_INVALID`, `VARIANT_INVALID`, `CATEGORY_CYCLE`, `RANGE_INVALID`, `ADJUSTMENT_INVALID`, `STOCK_NEGATIVE`, `STATS_RANGE_INVALID`, `TOKEN_INVALID`, `PASSWORD_TOO_WEAK`, `CURRENT_PASSWORD_INVALID`, `CONFIRMATION_REQUIRED`, `LAST_SIGN_IN_METHOD`, `EMAIL_TAKEN`, `EMAIL_UNCHANGED`, `ADDRESS_LIMIT_REACHED`, `COUNTRY_INVALID`, `DATE_INVALID`, `LAST_SHIPMENT`, `CARRIER_UNKNOWN`, `DELIVERY_ESTIMATE_INVALID`, `COUPON_INVALID`, `COUPON_EXPIRED`, `COUPON_MIN_ORDER_NOT_MET`, `COUPON_USAGE_LIMIT_REACHED`, `COUPON_ALREADY_USED`, `COUPON_NOT_APPLICABLE`, `COUPON_VALUE_INVALID`, `ORDER_TOTAL_ZERO`, `LIVE_ANIMAL_CONDITIONS_REQUIRED`, `REFUND_AMOUNT_INVALID`, `REFUND_REFUSED` |
| 413 | `FILE_TOO_LARGE` (uploads over 15 MB) |
| 423 | `ACCOUNT_LOCKED` |
| 429 | `RATE_LIMITED` (with `Retry-After` header) |
| 500 | `INTERNAL_ERROR` (no stack traces or internals in the body) |
| 503 | `PAYMENT_PROVIDER_UNAVAILABLE` (Stripe could not be reached or refused the call; try again later) |

### 1.5 Idempotency and concurrency

- `POST /checkout/orders` requires an `Idempotency-Key` header (16–100 characters of
  `A–Z a–z 0–9 _ -`, e.g. a UUID, generated by the client per checkout attempt).
  Repeating the request with the same key returns the order created the first time.
  The client keeps the key when the answer was lost (network error, 5xx) and takes a
  new one after the server refused the attempt (4xx).
- Admin updates of products, orders and coupons send the `version` they edited;
  a stale version returns `409 CONFLICT`.

### 1.6 Server-side authority

The API **ignores** any price, total, discount, tax or stock value sent by a
client. Requests contain only identifiers and quantities; every amount in a
response is calculated by the server.

### 1.7 Texts in two languages

Texts the owner writes (products, pack sizes, photo descriptions, categories, species,
colours, grades, shipping methods, gallery photos, coupon notes) have an English version
and an optional German one. Public responses carry **one** text per field, chosen by
`Accept-Language`: the German text where it is written, otherwise the English one
(docs/adr/012-language-in-links.md). Search (`q`) matches both languages; facets and the
name sort use the chosen language. Orders keep the names in the customer's language.

Public product and species details add `languages`: the languages their own texts are
written in (`["en"]` or `["en", "de"]`; German counts once the German description or, for
products, short description is written). The SPA keeps a German page out of search engines
(`noindex`) until it is listed there.

Admin responses carry both versions side by side: every text field `x` has an `xDe`
(`nameDe`, `descriptionDe`, …), `null` while not translated. Requests take the same
optional `…De` fields with the same length limits; blank values are stored as `null`.

## 2. Endpoint overview

### 2.1 Auth — `/api/v1/auth`

| Method | Path | Access | Description |
|---|---|---|---|
| GET | `/auth/csrf` | public | Ensures the `XSRF-TOKEN` cookie is set (called on app start) |
| POST | `/auth/register` | public | `{ email, password, firstName, lastName, marketingOptIn? }`. Sends a verification email. Always `202` |
| POST | `/auth/login` | public | `{ email, password }` → `200` session view + `SESSION` cookie (new session id on every login). The guest cart is merged on the next cart request (§2.4) |
| POST | `/auth/logout` | public | Ends the session; `204` even without one |
| GET | `/auth/me` | public | `{ "authenticated": true, "user": { id, email, firstName, lastName, role } }` or `{ "authenticated": false, "user": null }` |
| POST | `/auth/verify-email` | public | `{ token }` from a registration **or** email-change email → `204` |
| POST | `/auth/resend-verification` | public | `{ email }` → always `202` |
| POST | `/auth/forgot-password` | public | `{ email }` → always `202` |
| POST | `/auth/reset-password` | public | `{ token, newPassword }` → `204`; ends all sessions of the user |
| GET | `/auth/sign-in-options` | public | `{ "google": true }` when signing in with Google is set up |
| GET | `/auth/google?returnTo=&intent=` | public | Opened as a page (a link, not fetch): `302` to Google. `intent=sign-in` (default) or `confirm` (signed in; see §2.6). `404` when Google is not set up |
| GET | `/auth/google/callback` | public | Google sends the browser back here: `302` to `returnTo` (signed in) or to a shop page with `?google=<code>` |

**Rules**

- **Login requires a verified email address.** Passwords: 10–128 characters, no
  composition rules, obvious choices rejected (`422 PASSWORD_TOO_WEAK`).
- **No account enumeration.** Register, resend and forgot-password always answer
  `202`; only the email that is sent differs (an existing address gets a "you
  already have an account" email, and its password is never replaced). Unknown
  address and wrong password both give `401 INVALID_CREDENTIALS`.
- **What is revealed only after the correct password:** `403 EMAIL_NOT_VERIFIED`
  and `423 ACCOUNT_LOCKED` (locked by an administrator).
- **Brute force:** after 10 wrong passwords in a row the account is locked for
  15 minutes; attempts are also limited per address (whether or not an account
  exists) and per IP. All three answer `429 RATE_LIMITED` with `Retry-After`,
  so a temporary lock does not reveal that the account exists.
- Emailed links are single-use (`422 TOKEN_INVALID` otherwise): verification
  and email change 48 h, password reset 1 h. Only a SHA-256 hash is stored.
- Emails are sent in the language of the request (`Accept-Language`: `en`/`de`).

**Sign in with Google** (ADR-014; OpenID Connect, authorization code flow)

- `returnTo` is where the customer comes back to, as the browser shows it (`/checkout`,
  `/de/kasse`); a German path makes a new account German and Google's pages German (`hl`).
  Only paths on this site are accepted: anything else (`https://…`, `//host`, `/api/…`,
  characters a link would have encoded) becomes `/account`.
- `/auth/google` keeps the authorization request in the session — random `state`, `nonce` and a
  PKCE verifier (S256) — and asks for `openid email profile` only. The callback only accepts
  Google's answer to the request kept in **this** browser session; the server exchanges the code
  with Google and checks the ID token's signature against Google's published keys, its issuer,
  audience, expiry and nonce. Google's access token is not kept.
- **Which account:** the Google account is found by Google's subject id (`sub`), not by its
  address. The first time, it is connected to the account with the same address, but only if
  Google says the address is verified (`email_verified`); the customer gets a "Sign-in with Google
  added" email. Was that account's address not confirmed yet, its password is removed (it was
  never proven by the address owner). Without an account, a new one is created — verified, no
  password, name from Google. Administrators sign in with their password only.
- Sign-in starts a new session (new session id, fresh CSRF token), as with a password.
- **Back to the shop with `?google=<code>`** (on the sign-in page, keeping `redirect=`; for
  `intent=confirm` on `returnTo`): `cancelled` (at Google), `failed` (Google's answer did not
  check out), `expired` (no flow started in this browser session, or used up), `unverified`,
  `locked`, `password_only` (administrators), `other_account` (the shop account is connected to
  a different Google account), `too_many` (rate limit), `not_connected` (confirming with a
  Google account that is not the connected one), `confirmed` (success of `intent=confirm`).
- Logged: only the reason of a failure (e.g. `invalid_id_token`), never tokens or personal data.

| Method | Path | Description |
|---|---|---|

**`GET /products` and `GET /products/facets` query parameters**

| Param | Example | Notes |
|---|---|---|
| `q` | `blue` | Text search on product name and species names (max 100 chars) |
| `category` | `neocaridina` | Category slug, includes sub-categories |
| `species` | `neocaridina-davidi` | Multi-value (repeated or comma-separated) |
| `colour` | `blue,red` | Multi-value |
| `grade` | `sss` | Multi-value |
| `minPrice`, `maxPrice` | `500`, `3000` | Cents, compared with the cheapest active variant |
| `availability` | `IN_STOCK` | `IN_STOCK` (incl. low stock), `COMING_SOON`, `ALL` (default) |
| `featured` | `true` | Featured products only |
| `sort` | `PRICE_ASC` | `RELEVANCE` (default), `NEWEST`, `PRICE_ASC`, `PRICE_DESC`, `NAME_ASC`, `GRADE_DESC` |
| `page`, `size` | `0`, `24` | Zero-based page; size 1–100, default 24 |

Only `ACTIVE` products of species that are not trade-restricted are ever returned.
`RELEVANCE` lists purchasable products first, then "coming soon", then sold out;
within each group featured first, then newest. Invalid values → `400 VALIDATION_FAILED`.

`OUT_OF_STOCK` (rules in DATABASE.md §3.2).

**Product detail** (`GET /products/{slug}`) adds `shortDescription`,
`descriptionHtml` and `careNotesHtml` (sanitised HTML rendered from Markdown),
`species` (with `care`: temperature, pH, GH, KH, TDS, size, lifespan, difficulty
— every value nullable), `categoryPath` (root first, for breadcrumbs),
`availableFrom`, `images[]`, `seo`, `languages` (§1.7) and:

```json
"variants": [
  { "id": "0193…a1", "sku": "BLUE-DREAM-PREMIUM-1", "name": "1 animal", "packSize": 1,
    "price": { "amount": 590, "currency": "EUR" }, "compareAtPrice": null,
    "available": true, "maxQuantity": 6 },
  { "id": "0193…a2", "sku": "BLUE-DREAM-PREMIUM-10", "name": "10 animals", "packSize": 10,
    "price": { "amount": 5200, "currency": "EUR" }, "compareAtPrice": null,

```

Exact stock numbers are never exposed: `maxQuantity` (packs that can be bought
now) is capped at 20, and low stock is only signalled as `availability: LOW_STOCK`.

**Facets** (`GET /products/facets`): options with counts for the current search.
Each dimension is counted *without its own filter*, so other options in the same
group stay selectable.

```json
{
  "species": [ { "slug": "neocaridina-davidi", "name": "Neocaridina shrimp", "hexCode": null, "count": 9 } ],
  "colours": [ { "slug": "blue", "name": "Blue", "hexCode": "#1565C0", "count": 2 } ],
  "grades":  [ { "slug": "high", "name": "High", "hexCode": null, "count": 3 } ],
  "availability": { "inStock": 14, "comingSoon": 1 },
  "price": { "min": { "amount": 190, "currency": "EUR" }, "max": { "amount": 1390, "currency": "EUR" } }
}
```

`GET /products/{slug}/related` returns up to 4 visible products: same species
first, then same category; purchasable ones first.

**Response conventions for generated types:** every property of a response
object is always present (marked `required` in OpenAPI); properties that can be
`null` are published as nullable. Request bodies are named `*Request`.

### 2.4 Cart — `/api/v1/cart` (public; guest or customer)

| Method | Path | Body | Description |
|---|---|---|---|
| GET | `/cart` | — | Current cart (an empty cart if there is none; never creates one) |
| POST | `/cart/items` | `{ variantId, quantity }` | Add packs (on top of an existing line). Creates the cart if needed |
| PATCH | `/cart/items/{itemId}` | `{ quantity }` | Set the quantity of a line |
| DELETE | `/cart/items/{itemId}` | — | Remove a line |
| DELETE | `/cart` | — | Empty the cart (and remove its coupon) |
| PUT | `/cart/coupon` | `{ code }` | Enter a coupon code (replaces one entered before) |
| DELETE | `/cart/coupon` | — | Remove the coupon |

**Who owns the cart**

- **Guests:** an `HttpOnly`, `SameSite=Lax` cookie `CART_TOKEN` (random 256-bit
  token, 30 days, renewed on every change). Only its SHA-256 hash is stored.
- **Customers:** one cart per account, found through the session.
- **After signing in:** the next cart request carries both the session and the
  guest cookie; the guest cart is merged into the account's cart (quantities
  summed, capped at the available stock) and the cookie is deleted. The cart then
  belongs to the account and is there again after signing out and in.

**Rules**

- Requests contain only ids and quantities (`quantity` 1–20). Any price field a
  client sends is ignored; prices, totals and VAT come from the catalog.
- Adding or changing: unknown variant → `404`; product not purchasable →
  `409 PRODUCT_UNAVAILABLE`; more than is in stock → `409 INSUFFICIENT_STOCK`;
  more than 50 different products → `422 CART_FULL`.
- A line of another visitor's cart → `404`.
- The cart does not reserve stock (that happens when the order is placed).
  On every read it is recalculated: a quantity above the available stock is
  lowered and saved (`QUANTITY_REDUCED`, reported once); a product that cannot be
  bought right now stays in the cart as `available: false`, is excluded from the
  totals and reported as `ITEM_UNAVAILABLE` until it is removed or back in stock.

Every call returns the full, recalculated cart:

```json
{
  "items": [
    {
      "id": "0193…c1",
      "variantId": "0193…a1",
      "productSlug": "blue-dream-high",
      "productName": "Blue Dream",
      "variantName": "1 animal",
      "speciesName": "Neocaridina davidi",
      "gradeName": "High",
      "categorySlug": "neocaridina",
      "colourHex": "#1565C0",
      "image": null,
      "quantity": 3,
      "maxQuantity": 12,
      "unitPrice": { "amount": 390, "currency": "EUR" },
      "lineTotal": { "amount": 1170, "currency": "EUR" },
      "available": true
    }
  ],
  "totals": {
    "subtotal":    { "amount": 1170, "currency": "EUR" },
    "discount":    { "amount": 117,  "currency": "EUR" },
    "total":       { "amount": 1053, "currency": "EUR" },
    "includedTax": { "amount": 168,  "currency": "EUR" }
  },
  "itemCount": 3,
  "warnings": [
    { "code": "QUANTITY_REDUCED", "itemId": "0193…c1", "productName": "Blue Dream", "quantity": 3 }
  ],
  "coupon": {
    "code": "SPRING10",
    "description": "Spring sale",
    "type": "PERCENTAGE",
    "percentage": 1000,
    "amount": null,
    "maxDiscount": null,
    "minOrder": null,
    "applied": true,
    "problem": null,
    "saving": { "amount": 117, "currency": "EUR" }
  }
}
```

`itemCount` is the number of packs in available lines (header badge). The cart has no
shipping yet, so `total` is `subtotal − discount`. Warning codes:
`QUANTITY_REDUCED`, `ITEM_UNAVAILABLE`, `ITEM_REMOVED`. A changed price needs no
warning here because the cart always shows the current price; the checkout
compares the total the customer saw with the server's (`PRICE_CHANGED`, Phase 5).

**Coupons**

A cart carries at most one coupon (one code per order). `coupon` is `null` without one.

- `PUT /cart/coupon` accepts a code (`code` 1–40 characters, any letter case) only if it
  reduces the cart right now; an empty cart → `409 CART_EMPTY`; otherwise `422` with the
  reason and the cart keeps its previous coupon: `COUPON_INVALID` (unknown, switched off or not started yet),
  `COUPON_EXPIRED`, `COUPON_USAGE_LIMIT_REACHED`, `COUPON_ALREADY_USED` (signed-in
  customer reached the per-customer limit), `COUPON_MIN_ORDER_NOT_MET`,
  `COUPON_NOT_APPLICABLE` (only reduced products in the cart). Rate limit `cart-coupon` (§5).
- A coupon that stops applying later (items removed, expired, used up) **stays** in the
  cart with `applied: false` and `problem` set to one of the codes above, so the customer
  sees why; `discount` is then `0`. It applies again once the reason is gone (e.g. more
  items added).
- Coupon fields: `type` `PERCENTAGE` (`percentage` in basis points, 1000 = 10 %),
  `FIXED_AMOUNT` (`amount`) or `FREE_SHIPPING`; `maxDiscount` caps a percentage; `minOrder`
  is the goods value (before the discount) needed; `saving` is what the coupon saves on
  this cart. A free-shipping coupon saves nothing in the cart (`discount` 0) — the
  shipping price is waived at checkout.
- How the discount is calculated (all in `pricing.PriceCalculator`, whole cents): it
  applies to the goods only, never to lines that are already reduced (a variant with a
  compare-at price); a percentage is rounded half-up and capped by `maxDiscount`; a fixed
  amount never exceeds the eligible goods. The discount is split over the eligible lines in
  proportion to their value (largest remainder), and the VAT of each rate is calculated on
  the reduced amounts.
- Coupons apply to the whole shop (no restriction to categories or products yet).
- After signing in, a guest's coupon comes along unless the account's cart already has one.
  The per-customer limit is checked as soon as the customer is known.

### 2.5 Checkout — `/api/v1/checkout` (customer)

Signed-in customers only. The customer and the cart always come from the session; a
request names an address of the customer and a shipping method, never items or prices.

| Method | Path | Description |
|---|---|---|
| GET | `/checkout/shipping-methods?country=DE` | Methods for the cart and a destination, with prices and dispatch dates |
| POST | `/checkout/quote` | Price breakdown for the cart, an address and a shipping method |
| POST | `/checkout/orders` | Place the order (requires `Idempotency-Key`, §1.5) → `201` |

Every call checks the cart first: empty → `409 CART_EMPTY`; a line that is no longer
available in the wanted quantity (also counting all pack sizes of a product together) →
`409 CART_CHANGED`. The checkout never changes quantities itself — the customer goes
back to the cart, which shows what changed (§2.4).

**`GET /checkout/shipping-methods`**

```json
{
  "methods": [
    {
      "code": "DHL_LIVE_DE",
      "name": "DHL Express – Germany",
      "description": "Insulated box, dispatched Monday to Wednesday.",
      "carrier": "DHL",
      "price": { "amount": 990, "currency": "EUR" },
      "freeFrom": null,
      "plannedDispatchDate": "2027-03-08",
      "estimatedDeliveryFrom": "2027-03-09",
      "estimatedDeliveryTo": "2027-03-09"
    }
  ],
  "paused": false,
  "pauseMessage": null,
  "pausedUntil": null
}
```

- Only methods that deliver to the country and may carry the cart (live animals need a
  method that allows them). No method → `methods` is empty.
- `price` is `0` once the goods value (after a coupon discount) reaches the method's
  `freeFrom` threshold, and for every method while the cart has a free-shipping coupon
  that applies.
- `plannedDispatchDate` is the **earliest** dispatch day: the first dispatch weekday of
  the method that is at least `SHIPPING_HANDLING_DAYS` (default 1) after today, in the
  shop's time zone. Public holidays are not considered yet.
- **Shipping pause** (shop setting `shipping.pause`, live animals only): with an end date
  the dispatch date moves behind it (`paused: true`, `pausedUntil`); without an end date
  no methods are offered and quote/order answer `409 SHIPPING_PAUSED`.

**`POST /checkout/quote`**


Response: `items` (cart lines with current names, prices and `lineTotal`), `totals`
(`subtotal`, `discount`, `shipping`, `total`, `includedTax`), the chosen `shippingMethod`
(as above), `containsLiveAnimals`, the cart's `coupon` (as in §2.4, or `null`) and the

is configured and the total is at least €0.50 (Stripe's minimum), `BANK_TRANSFER` while the
shop's bank account is (e.g. `["STRIPE", "BANK_TRANSFER"]`; empty when neither is).

Coupon order of calculation: the discount comes off the goods first; the goods value after
the discount decides `freeFrom` thresholds; a free-shipping coupon then waives the shipping
price (`shipping` 0, its `saving` is the waived price). `total` = `subtotal − discount + shipping`.
Another customer's address → `404`; a method that does not fit → `409 SHIPPING_METHOD_UNAVAILABLE`.

**`POST /checkout/orders`**

- `billingAddressId` omitted or `null`: billed to the shipping address. Addresses are
  always saved addresses of the customer (a new one is created through §2.6 first).
- `acceptedTerms` must be `true` (`400 VALIDATION_FAILED`); with live animals in the
  cart `acceptedLiveAnimalConditions` must be `true` too
  (`422 LIVE_ANIMAL_CONDITIONS_REQUIRED`).
- `expectedTotal` is **not** used for pricing. If it differs from the server's total the
  request fails with `409 PRICE_CHANGED`, so nobody pays an amount they have not seen.
- Unknown fields such as items or prices are ignored.
- The coupon comes from the cart, never from the request. If it stopped applying since the
  quote (e.g. the last use was taken meanwhile), the request fails with that coupon's code
  (`422 COUPON_USAGE_LIMIT_REACHED`, `COUPON_EXPIRED`, …) instead of `PRICE_CHANGED`, and
  the cart shows the coupon with its `problem`.
- Other refusals: `409 PAYMENT_METHOD_UNAVAILABLE`, `409 INSUFFICIENT_STOCK` (final
  guard while taking the stock), `422 ORDER_TOTAL_ZERO` (nothing to pay, e.g. a coupon
  covering everything; such orders are taken by the shop directly), `429 RATE_LIMITED`.

In one transaction the server locks the cart, the products and then the coupon, checks
everything again, takes the animals out of stock, stores the order with snapshots of items,
prices, discount, coupon code and addresses, records the coupon's use (a conditional
update of its counter, so the last use cannot be taken twice), empties the cart and queues
the confirmation email (for card payment it
contains the link to the payment page and the deadline; for bank transfer, the bank details).

**`POST /payments/stripe/intents`**

```json
{ "orderNumber": "PW-2027-000123" }
```

```json
{
  "orderNumber": "PW-2027-000123",
  "amount": { "amount": 1770, "currency": "EUR" },
  "paymentDueAt": "2027-03-01T10:12:00Z",
  "clientSecret": "pi_…_secret_…",
  "publishableKey": "pk_live_…",
  "alreadyPaid": false
}
```

- The first call creates the Stripe PaymentIntent for the **stored order total** (one per
  order, Stripe idempotency key `order-<id>-intent`); later calls — a reload, another card
  after a decline — return the same one. Amounts in the request are ignored.
- `clientSecret` and `publishableKey` go to Stripe.js (`Elements` + Payment Element,
  `confirmPayment` with `redirect: "if_required"` and the confirmation page as `return_url`).
  The publishable key is public by design; it comes from the API so the frontend build
  needs no Stripe configuration.
- `alreadyPaid: true` (and `clientSecret: null`): Stripe already has the money; the order
  turns `PAID` as soon as the webhook arrives.
- Refusals: another customer's or an unknown order → `404`; malformed number → `400`;
  `409 ORDER_ALREADY_PAID`; `409 ORDER_NOT_PAYABLE` (cancelled or past `paymentDueAt`);
  `409 PAYMENT_METHOD_UNAVAILABLE` (not a card order, or Stripe not configured);
  `503 PAYMENT_PROVIDER_UNAVAILABLE`; `429 RATE_LIMITED`.

**The order is paid only through the webhook.** What the browser reports after
`confirmPayment` is never trusted; the confirmation page asks for the order status until
the server has heard from Stripe.

**`POST /webhooks/stripe`** — configured in the Stripe Dashboard (Developers → Webhooks)
for `payment_intent.succeeded`, `payment_intent.processing`, `payment_intent.payment_failed`,
`payment_intent.canceled`, `charge.refunded`, `refund.updated` and `refund.failed`
(older API versions send `charge.refund.updated` instead, which is handled the same); its
signing secret is `STRIPE_WEBHOOK_SECRET`.

- The `Stripe-Signature` header is checked against the raw body (5 minutes tolerance);
  missing or wrong → `400 WEBHOOK_SIGNATURE_INVALID`. A signed body that is not an event →
  `400 WEBHOOK_INVALID`. Bodies over 256 KB are refused. Without a configured Stripe
  account the endpoint answers `404`.
- Each event is stored once per Stripe event id (`payment_webhook_events`), reduced to ids,
  amounts and statuses, and processed in one transaction with its effect on the order;
  a repeated delivery changes nothing. If processing fails, the answer is `500` and
  Stripe delivers again later.
- `payment_intent.succeeded`: the amount and currency must equal the stored payment
  (otherwise nothing changes and the event is noted as `amount mismatch`); the order turns
  `PAID`, the customer gets a "payment received" email. If the order had been cancelled in
  the meantime it stays cancelled and the shop inbox is told, so the owner can refund.
- `payment_intent.payment_failed` records the decline reason; the order stays open and
  can be paid with another card until `paymentDueAt`.
- `charge.refunded` (refunds from the admin order page or the Stripe Dashboard) sets
  `paymentStatus` to `PARTIALLY_REFUNDED` or `REFUNDED` from Stripe's total; the order status
  stays for the owner to decide. A refund the admin page already counted changes nothing.
- `refund.updated` / `refund.failed` / `charge.refund.updated` for a refund made from the admin
  page: `succeeded` marks it as refunded; `failed` or `canceled` (e.g. the card account was
  closed, also after it had succeeded) takes the amount back off the refunded total, records
  Stripe's `failure_reason`, and tells the shop inbox so the owner can pay it back another way.
  Refunds made in the Dashboard are not listed and only count through `charge.refunded`.
- Events for PaymentIntents the shop did not create, and other event types, are
  acknowledged (`204`) and ignored.

**Local development:** Stripe cannot reach `localhost`. Forward events with the Stripe CLI
(`stripe listen --forward-to localhost:8080/api/v1/webhooks/stripe`, then use the
`whsec_…` it prints as `STRIPE_WEBHOOK_SECRET`).

**`POST /payments/paypal/orders`** — `{ "orderNumber": "PW-2027-000123" }`

```json
{
  "orderNumber": "PW-2027-000123",
  "amount": { "amount": 1770, "currency": "EUR" },
  "paymentDueAt": "2027-03-01T10:12:00Z",
  "paypalOrderId": "5O190127TN364715T",
  "clientId": "A…",
  "alreadyPaid": false
}
```

- The first call creates the PayPal order for the **stored order total** (one per order,
  `PayPal-Request-Id: order-<id>`, `intent: CAPTURE`, no shipping address asked for or
  returned, PayPal's pages in the customer's language); later calls return the same one.
  Amounts in the request are ignored.
- `clientId` loads PayPal's script (public by design); the button opens `paypalOrderId`.
- `alreadyPaid: true` (and `paypalOrderId: null`): PayPal has the money or is still checking it.
- Refusals as for card payment: `404`, `400`, `409 ORDER_ALREADY_PAID`, `409 ORDER_NOT_PAYABLE`,
  `409 PAYMENT_METHOD_UNAVAILABLE` (not a PayPal order, or PayPal not configured),
  `503 PAYMENT_PROVIDER_UNAVAILABLE`, `429 RATE_LIMITED`.

**`POST /payments/paypal/captures`** — `{ "orderNumber": "PW-2027-000123" }` →
`{ "orderNumber": "…", "status": "PAID" | "PENDING" | "DECLINED" }`

- The server captures the PayPal order (`PayPal-Request-Id: order-<id>-capture`, so a repeated
  call takes nothing twice) and reads the result **from PayPal**. `PAID`: the order is paid now
  (the customer gets the "payment received" email). `PENDING`: PayPal or the bank still checks
  the payment; the webhook completes it, and the order can neither be cancelled nor expire
  meanwhile. `DECLINED`: nothing was taken (the funding source was declined, or the customer
  has not approved yet); the browser lets the customer choose another way to pay in PayPal's
  window. The decline reason is kept (`INSTRUMENT_DECLINED`, `ORDER_NOT_APPROVED`).
- Refusals as above, plus `409 PAYMENT_NOT_STARTED` (no PayPal order yet).

**`POST /webhooks/paypal`** — registered for the REST app (developer.paypal.com → Apps &
Credentials → the app → Webhooks) for `CHECKOUT.ORDER.APPROVED`, `PAYMENT.CAPTURE.COMPLETED`,
`PAYMENT.CAPTURE.PENDING`, `PAYMENT.CAPTURE.DENIED`, `PAYMENT.CAPTURE.DECLINED`,
`PAYMENT.CAPTURE.REFUNDED` and `PAYMENT.CAPTURE.REVERSED`; its id is `PAYPAL_WEBHOOK_ID`.

- PayPal confirms each delivery: the `PAYPAL-*` headers and the body exactly as received go to
  PayPal's verify-webhook-signature API with our webhook id; missing headers or anything but
  `SUCCESS` → `400 WEBHOOK_SIGNATURE_INVALID`. A body that is not exactly one JSON event →
  `400 WEBHOOK_INVALID`. Bodies over 256 KB are refused. Without PayPal configured → `404`.
- Stored once per PayPal event id, reduced to ids, amounts and statuses (no payer name or email),
  processed in one transaction with its effect on the order; a failure answers `500` and PayPal
  delivers again.
- `CHECKOUT.ORDER.APPROVED`: captured as above if the order still waits for payment (covers a
  customer whose browser never came back); otherwise noted as `order not awaiting payment`.
- `PAYMENT.CAPTURE.COMPLETED`: the amount and currency must equal the stored payment (otherwise
  noted as `amount mismatch`); the order turns `PAID` once. `…PENDING` keeps it waiting;
  `…DENIED`/`…DECLINED` record the reason. A capture completed for a cancelled order leaves it
  cancelled and tells the shop inbox, as for Stripe.
- `PAYMENT.CAPTURE.REFUNDED`/`REVERSED` (refunds from the admin order page or the PayPal
  account) set `paymentStatus` to `PARTIALLY_REFUNDED` or `REFUNDED` from the total refunded so
  far. For a refund made from the admin page, `COMPLETED` marks it as refunded (it may have been
  `PENDING` until then).

**Local development:** PayPal cannot reach `localhost`; a payment completes without webhooks
because the server captures it. To try webhooks, register a public address (e.g. a tunnel).

## 3. Admin API — `/api/v1/admin` (role `ADMIN`)

Every write is recorded in the audit log.

### 3.1 Dashboard and statistics

Read only; implemented as a read model in the `admin` module.

**Periods.** `from` and `to` are ISO dates, both inclusive, on the shop's calendar
(Europe/Berlin). Without them the last 30 days up to today are used. A period may be at most
731 days; `to` before `from` or a longer period → `422 STATS_RANGE_INVALID`; a malformed date →
`400`. The bucket size follows the length: up to 31 days per day, up to 182 days per week
(Monday–Sunday), longer per month. Every figure is compared with the period of the same length
directly before (`period.previousFrom`/`previousTo`).

**Definitions.** A *sale* is an order that is neither cancelled (expired unpaid orders are
cancelled too) nor refunded, counted on the day it was placed. Amounts are gross (incl. VAT);
order totals include shipping, product and category figures use line totals (goods only).
*Paid* means `paymentStatus` `PAID` or `PARTIALLY_REFUNDED`. *Animals* are packs × animals per
pack of live-animal lines. Changes and shares are in basis points (`changeBps`: +12.5 % = 1250;
`null` when the previous value was 0). All figures, shares and averages are calculated by the
server (half-up rounding); the admin pages only format them.

  `descriptionDe?`), `origin?` (`originDe?`), care data (`tempMinC`/`tempMaxC`,
  `phMin`/`phMax`, `ghMin`/`ghMax`, `khMin`/`khMax`, `tdsMin`/`tdsMax`, `adultSizeMm`,
  `lifespanMonths`, `difficulty`), `tradeRestricted`, `restrictionNote?`
  (`restrictionNoteDe?`, both kept only while restricted). A minimum above
  its maximum → `422 RANGE_INVALID`. Marking a species as restricted removes all its
  products from the shop at once.
- **Colours:** `name` (`nameDe?`), `slug?`, `hexCode?` (`#RRGGBB`), `sortOrder`.
- **Grades:** `name` (`nameDe?`), `slug?`, `scale?`, `description?` (`descriptionDe?`), `rank`
  (0–1000, higher is better),
  `sortOrder`.

Deleting something still used by a product (or a category with sub-categories) →
`409 IN_USE`.

### 3.6 Coupons

| Method | Path | Description |
|---|---|---|
| GET | `/admin/coupons?q=&status=` | All coupons, newest first (`q`: part of the code or note; `status` as below) |
| POST | `/admin/coupons` | Create → `201` |
| GET | `/admin/coupons/{id}` | One coupon |
| PUT | `/admin/coupons/{id}` | Update; requires the `version` that was edited (missing → `400`, stale → `409 CONFLICT`). Switching on/off is an update of `active` |
| DELETE | `/admin/coupons/{id}` | Delete a coupon no order has used (`204`; it is taken out of carts). Used → `409 COUPON_IN_USE` — switch it off instead |
| GET | `/admin/coupons/{id}/usage` | Orders that used it and count as sales (§3.1): `orders`, `saving`, `revenue` |
| GET | `/admin/coupons/{id}/redemptions?page=&size=20` | Paged, newest first: `orderNumber`, `placedAt`, `customerName` (billing name), `orderStatus`, `orderTotal`, `saving`, `released` (the order was cancelled and the use given back) |

**Request** (`POST`, `PUT`):

```json
{
  "code": "SPRING10",
  "description": "Spring sale",
  "descriptionDe": "Frühlingsaktion",
  "type": "PERCENTAGE",
  "value": 1250,
  "minOrderCents": 3000,
  "maxDiscountCents": 2000,
  "startsOn": "2027-03-01",
  "endsOn": "2027-03-31",
  "usageLimitTotal": 100,
  "usageLimitPerCustomer": 1,
  "active": true,
  "version": 0
}
```

- `code`: 3–32 of `A–Z 0–9 _ -`, starting with a letter or digit; stored in upper case and
  compared case-insensitively; unique (`409 CODE_TAKEN`). It cannot be changed after
  creation (ignored on `PUT`).
- `value`: basis points for `PERCENTAGE` (1–10 000), cents for `FIXED_AMOUNT` (≥ 1), `0`
  for `FREE_SHIPPING`. `maxDiscountCents` only for percentages. A value or cap that does
  not fit the type → `422 COUPON_VALUE_INVALID`.
- `minOrderCents` (optional, default 0): goods value before the discount, without shipping.
- `startsOn`/`endsOn` (optional): shop calendar days, both inclusive (stored as the start of
  the first day and the start of the day after the last, Europe/Berlin); `endsOn` before
  `startsOn` → `422 RANGE_INVALID`.
- `usageLimitTotal` (1–1 000 000) and `usageLimitPerCustomer` (1–1 000) are optional
  (`null` = unlimited).

**Response** (`AdminCouponView`): the fields above as `percentage`/`amount`/`maxDiscount`/
`minOrder` (Money), plus `id`, `timesRedeemed`, `status`, `createdAt`, `updatedAt`,
`version`. `status` is decided by the server: `INACTIVE` (switched off), `EXPIRED`,
`SCHEDULED` (not started), `USED_UP` (total limit reached) or `ACTIVE`, in that order.

Every write is recorded in the audit log (`COUPON_CREATED`, `COUPON_UPDATED`,
`COUPON_DELETED`). Cancelling an order (customer, owner or expiry) gives its coupon use
back: the redemption is kept with `released` and the counter goes down.
